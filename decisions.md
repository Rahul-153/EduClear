## D-43 — Checkout fallback for a hung PayPal pop-up (2026-11-07)
PayPal's sandbox login pop-up can stay on its spinner after the buyer signs in, so the SDK `onApprove` never fires. The checkout now retries the capture every 4 s for 3 minutes after the PayPal button is clicked and offers a "check my payment" link. PayPal refuses capture until the buyer approves, and capture is idempotent in the ledger, so a premature attempt is harmless.

## D-52 — Accounts: families own records through the existing owner column (2026-11-11, branch feature/auth)
Phases 1 and 2 of `PLAN_AUTH.md` use the defaults the plan recommended: email one-time code (6 digits, 10 minutes, 5 attempts, 5 per email and 20 per IP per hour), no passwords, server-side sessions with a hashed id in an HttpOnly SameSite=Lax cookie, parent-invite only for students under 18, one parent and one student per family, parent-only payments and deposit changes. Deviation from the plan: no new columns on `Booking` or `Deposit`. A signed-in family writes `owner = "family:<id>"`, a signed-in user without a family `user:<id>`, a guest keeps the browser id; guest ids are limited to letters, digits, `-` and `_`, so they can never collide with the prefixes. Reason: no migration is needed on the live Postgres (D-35); only new tables are created. Consequence: records stay with the family id when members leave. Guest checkout stays open while `GUEST_CHECKOUT=true` (default), so the live demo and smoke script are unchanged; the CSRF check (`X-Requested-With: educlear`) applies only to requests that carry a session cookie. A mock mailer is the only delivery channel: with `ENV=production` sign-in answers 503 until a real provider exists, and `AUTH_SHOW_CODE=true` (demo only, never in production) returns the code in the response. Not built: server-side survey and profile (plan phase 3), guest-data claim, export and delete, CSP headers, real mail provider, children's-data legal check. Local dev databases created before this change need the new tables dropped if their columns change (no migrations).

## D-53 — Accounts review fixes: safe production defaults (2026-11-12, branch feature/auth)
`render.yaml` now sets `ENV=production` and a Render-generated `AUTH_SECRET`, and the app refuses to start with `ENV=production` and no secret (a per-process key would void every invite and pending code on each restart). Until a real mail provider exists (T-11.04) this means sign-in is off on the live site: `/api/auth/start` answers 503, `/api/auth/me` returns `sign_in_available: false` and the header hides the Sign in link; guests are unchanged. The Docker command adds `--proxy-headers --forwarded-allow-ips '*'` so the per-IP code limit sees the visitor's address and `request.base_url` is https; the service is reachable only through Render's proxy, and a forged `X-Forwarded-For` can only dodge the per-IP limit, not the per-email one. ## D-54 — OpenCode free model as a hosted LLM provider (2026-11-12, branch feature/opencode-llm)
Added `opencode` to `backend/app/llm/client.py`: OpenAI-compatible chat completions at `https://opencode.ai/inference/openai/v1` (the older `/zen/v1` path still answers), model `deepseek-v4.1-flash-free` (free, 200k context, reasoning and structured output supported), Bearer key from `LLM_API_KEY`. Both facts come from OpenCode's public catalog, `https://opencode.ai/zen/v1/models`, read 2026-11-12; the `deepseek-v4-flash-free` id quoted by some third-party pages is not in it. Choices: (1) the model is a reasoning model, so `max_tokens` is 1500 and timeout 90 s for this provider (400 and 60 s elsewhere); no reasoning parameter is sent because its request field name is not documented; `reasoning_content` is never used as an answer; (2) if the gateway rejects `response_format` (400 or 422) the JSON call is retried once without it; (3) `HostedLLM.last_error` holds a key-free reason (status and the gateway's error text) and `scripts/llm_smoke.py` prints it; (4) an empty `LLM_MODEL` with `LLM_PROVIDER=opencode` means the default model; (5) emails and phone numbers are still redacted before any text leaves (NFR-02), and every failure still falls back to the rules path, so the app cannot break because of this provider. Caveat on record: OpenCode's docs say free chat models "require OpenCode" and are not meant for other clients, and a request with no key gets HTTP 429 FreeUsageLimitError ("Free models work in OpenCode"); a fake key gets 401. Whether a real console key is accepted for calls from this app was not tested (no key). Run `scripts/llm_smoke.py` with the key in `.env` to find out. Per the docs page, this model has a zero-retention, no-training policy and the free period is time-limited with no end date given.

## D-55 — Local Ollama as a fallback behind the hosted model (2026-11-12, branch feature/opencode-llm)
Live test of D-54: the OpenCode free model answers `429 FreeUsageLimitError` with the owner's key, and its `Retry-After` of 34,255 s from 14:29 UTC ends at 00:00 UTC, which reads as a daily free quota that resets at midnight UTC (05:30 IST); whether the free model is usable from outside OpenCode's own app is still unconfirmed. So `get_llm()` now returns `FallbackLLM(hosted, ollama)` when a hosted provider is configured, Ollama is running (probed, cached 30 s) and `LLM_LOCAL_FALLBACK` is not false: the hosted model is asked first and the local model answers only if it returns nothing (error, rate limit, empty). A 429 pauses that hosted model for its Retry-After, between 60 s and 1 h, shared across requests, so a reached limit is not hit on every call and the hosted model is retried at least hourly (it resumes by itself after the reset). Explicit `LLM_PROVIDER=ollama` or `auto` stay local only; with no key and Ollama down the app uses rules, as before. Local text mode fix: on Ollama 0.13.5 `qwen3:4b` writes its reasoning into `message.content` when `think=false`, so plain text calls use `think=true` (answer in `content`, reasoning in `thinking`, never used) with `num_predict` 1000; JSON calls keep `think=false`, the schema and 400 tokens. `FallbackLLM.name` is whichever model answered last. Live result: both calls answered by `ollama:qwen3:4b` (text 6 s, JSON 1 s); intake filled 'South' for "near Chennai" (source `llm`, guarded against the text) and the agent routed an ambiguous message through the local model (3 to 5 s). The 4B model did not fill every field it could (for example "twenty lakhs" or a Hindi percentile). Rephrasing (`LLM_PHRASING`) stays off by default.
