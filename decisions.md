## D-43 — Checkout fallback for a hung PayPal pop-up (2026-11-07)
PayPal's sandbox login pop-up can stay on its spinner after the buyer signs in, so the SDK `onApprove` never fires. The checkout now retries the capture every 4 s for 3 minutes after the PayPal button is clicked and offers a "check my payment" link. PayPal refuses capture until the buyer approves, and capture is idempotent in the ledger, so a premature attempt is harmless.

## D-52 — Accounts: families own records through the existing owner column (2026-11-11, branch feature/auth)
Phases 1 and 2 of `PLAN_AUTH.md` use the defaults the plan recommended: email one-time code (6 digits, 10 minutes, 5 attempts, 5 per email and 20 per IP per hour), no passwords, server-side sessions with a hashed id in an HttpOnly SameSite=Lax cookie, parent-invite only for students under 18, one parent and one student per family, parent-only payments and deposit changes. Deviation from the plan: no new columns on `Booking` or `Deposit`. A signed-in family writes `owner = "family:<id>"`, a signed-in user without a family `user:<id>`, a guest keeps the browser id; guest ids are limited to letters, digits, `-` and `_`, so they can never collide with the prefixes. Reason: no migration is needed on the live Postgres (D-35); only new tables are created. Consequence: records stay with the family id when members leave. Guest checkout stays open while `GUEST_CHECKOUT=true` (default), so the live demo and smoke script are unchanged; the CSRF check (`X-Requested-With: educlear`) applies only to requests that carry a session cookie. A mock mailer is the only delivery channel: with `ENV=production` sign-in answers 503 until a real provider exists, and `AUTH_SHOW_CODE=true` (demo only, never in production) returns the code in the response. Not built: server-side survey and profile (plan phase 3), guest-data claim, export and delete, CSP headers, real mail provider, children's-data legal check. Local dev databases created before this change need the new tables dropped if their columns change (no migrations).

## D-53 — Accounts review fixes: safe production defaults (2026-11-12, branch feature/auth)
`render.yaml` now sets `ENV=production` and a Render-generated `AUTH_SECRET`, and the app refuses to start with `ENV=production` and no secret (a per-process key would void every invite and pending code on each restart). Until a real mail provider exists (T-11.04) this means sign-in is off on the live site: `/api/auth/start` answers 503, `/api/auth/me` returns `sign_in_available: false` and the header hides the Sign in link; guests are unchanged. The Docker command adds `--proxy-headers --forwarded-allow-ips '*'` so the per-IP code limit sees the visitor's address and `request.base_url` is https; the service is reachable only through Render's proxy, and a forged `X-Forwarded-For` can only dodge the per-IP limit, not the per-email one.
